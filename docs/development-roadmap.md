# AI 任务开发工作台分阶段开发计划

日期：2026 年 10 月 28 日。状态：开发提案。现状核对基于提交 `9b9e29d` 及当前工作区。

产品方向：以任务组织跨项目开发，统一准备工作现场、指派 AI 执行、检查结果，并支持人工随时接手。

先完成手动指定 bot 的开发闭环，再连接任务来源和第二种 coding agent，最后验证自动分配。阶段按验收结果推进，不预设日期；自动调度是否值得继续，以实际使用中的分配成本、验收和返工记录决定。

这条路线将当前个人开发工作台扩展为受监督的 AI 任务执行工作台。任务仍是一级入口，项目提供仓库资源，会话保持独立。本文提出后续范围，本轮仅新增计划文档，不修改业务代码或现行 AGENTS.md。

## 项目现状与可复用能力

| 能力 | 当前情况与依据 | 后续处理 |
| --- | --- | --- |
| 任务组织多个项目 | `internal/task/requirements.go`、`requirement_projects.go` 支持创建任务、新建或复用 worktree、追加和调整成员 | 直接复用，继续集中展示各项目实际目录、分支和修改状态 |
| 任务上下文 | 任务目标保存在数据库，按需生成 WORK_HUB_CONTEXT.md；会话创建时解析主目录和额外目录 | 执行前生成目标和目录快照，复用已有目录校验 |
| 独立会话及任务引用 | `internal/model/session.go`、`internal/session/scope.go`、`docs/session-architecture.md` 已将会话与任务解耦 | 执行记录引用会话，不把会话改造成任务的私有对象 |
| Codex 交互执行 | `internal/session/service.go`、`session_create.go`、`session_chat.go` 已提供实时事件、后台执行、审批、提问、停止和继续 | 在现有执行链上增加 bot 和执行记录，避免另建聊天系统 |
| 运行持久化 | 当前 ChatRun 由进程内映射管理；会话索引、创建请求和部分输入投递记录已经持久化 | 新增持久化的任务执行记录；服务重启后核实运行，不承诺进程重启后无缝继续执行 |
| 运行互斥 | 同一会话控制互斥；`concurrent_sessions_test.go` 明确允许不同会话在同一目录并行 | bot 执行新增目录占用规则，覆盖主目录和额外目录；保留普通独立会话的现有语义 |
| 改动与收尾 | `frontend/workspace/task-review.tsx`、`internal/project/cleanup.go` 已提供改动预览和 worktree 清理检查 | 复用改动预览；另建目标验收，区分代码验收和目录清理 |
| 执行环境 | 本机和 Windows 接入的 WSL 有独立数据与连接，通过环境标识路由 | bot 可用性和执行记录必须绑定环境，不能串用路径和身份 |
| 数据和测试 | SQLite 迁移、`internal/store/metadata.go` 元数据导入导出及 `.github/workflows/checks.yml` 已存在 | 新数据随阶段加入迁移、备份和对应回归验证 |
| 外部任务与 bot | 当前任务模型未包含外部 issue 身份、bot 注册及调度策略；会话服务直接使用 Codex 客户端 | 作为新增能力逐步实现；`internal/workspace/agent.go` 是环境辅助程序，不是 coding agent 注册中心 |

## 概念与实现边界

| 概念 | 职责 |
| --- | --- |
| 任务 | 保存目标、验收条件、参与项目和工作现场；可来自手动录入或外部 issue |
| 任务来源 | 保存外部系统、账号或实例范围、仓库或项目、issue 标识、原始链接和导入快照 |
| Agent 适配器 | 连接实际 coding 工具，报告其支持的创建、继续、停止、审批和历史读取能力 |
| Bot | 可复用执行配置，包括 agent、模型、指令、权限、适用环境和能力标签；初期不需要平台机器人账号或常驻进程 |
| 执行记录 | 一次明确指派的尝试，保存任务、bot 配置快照、工作现场、关联会话、状态、结果及验收引用 |
| 会话 | agent 的交互上下文，独立于任务和执行记录；一次执行可以包含多轮交互 |
| 验收记录 | 人工对目标是否达成的判断、理由和证据，关联本次执行及目标版本 |

任务准备状态、执行状态和验收状态分别表达。现有 `requirements.state` 的目录准备及归档语义保留；agent 结束一轮只更新执行信息，不能直接将任务标记为完成。归档任务、验收通过和清理 worktree 是不同操作。

首次 bot 执行默认创建新会话并关联任务。继续同一次尝试可以复用其会话；更换 bot 默认创建新会话，将已确认的目标和结果摘要作为交接信息，不假设不同工具之间可以迁移原生会话。

任务目标、验收条件和 bot 配置在执行开始时保存快照。之后编辑配置不改变历史记录；修改任务目标后，旧验收结论仍可追溯，但不能直接代表新目标已经通过。

## 阶段总览

| 阶段 | 交付结果 | 前置条件 | 优先级 |
| --- | --- | --- | --- |
| 0 | 确定概念、状态和验收样例 | 本计划 | 开工前完成 |
| 1 | 使用现有 Codex 手动指派 bot 并验收结果 | 阶段 0 | 首个开发里程碑 |
| 2 | 从一个任务源按需导入 issue | 阶段 1 | 近期 |
| 3 | 接入第二种 coding agent | 阶段 1 | 近期；与阶段 2 无硬依赖 |
| 4 | 验证第二任务源并提供 bot 推荐 | 阶段 2、3；存在实际使用需求 | 按需推进 |
| 5 | 按明确规则自动分配和排队 | 阶段 4 的手动分配记录 | 中期 |
| 6 | 受限运行任务分配机器人 | 阶段 5 稳定且规则存在明确不足 | 实验 |

阶段 1 至 3 完成后先持续自用，再决定阶段 4 至 6 的投入。第二任务源和智能调度均不以“凑齐功能”为启动依据。

## 阶段 0 确定任务执行和验收约定

解决的问题：避免将现有会话轮次、目录准备状态误当作新任务执行流程，减少后续数据和界面返工。

开发前完成以下设计：

1. 确定任务、bot、执行记录和验收记录的关系，以及执行状态的转换条件。
2. 执行状态至少覆盖准备启动、运行中、等待人工、执行结束、失败、已取消、待核实；验收单独表达未验收、通过和需返工。中间状态名称可以在实现时精简。
3. 明确接手操作：补充当前执行、停止后手动处理、使用新 bot 发起新尝试，均保留历史。
4. 准备统一验收样例：单仓库修复、前后端双仓库修改、执行中提问、启动结果不明、服务重启、已有修改目录、目录占用和验收返工。
5. 将本路线与 AGENTS.md 的现行范围对齐，作为后续正式修改产品范围说明的依据。

验收标准：每个样例都能明确回答“在哪个环境、用哪个 bot、改哪些目录、当前谁需要操作、怎样认定完成”，且不要求会话拥有任务或自动迁移旧工作目录。设计不引入团队权限、通用工作流引擎或机器人市场。

## 阶段 1 完成手动指派 bot 的开发闭环

解决的问题：任务已有工作现场，但每次仍需手动配置 agent、整理执行上下文和判断结果，缺少可追溯的指派与验收。

实施内容：

1. 增加最小 bot 配置，先只支持现有 Codex。保存名称、模型及思考强度、执行指令、权限和可用环境；提供创建、编辑、停用。权限作为可见的显式配置保存。
2. 在任务页增加选择 bot 和开始执行入口。执行前展示最新任务目标、验收条件、主目录和额外目录；复用现有成员选择与路径校验。首版一次执行固定在一个执行环境。
3. 增加持久化执行记录，关联配置快照、目标快照、会话、开始结束时间和状态。请求重试复用同一次启动结果；启动结果不明时进入待核实，不隐式重复发送。
4. 为受管理的 bot 执行增加目录占用检查，覆盖全部可写目录及父子目录重叠；多个目录作为整体获取占用，避免只占住一半。遇到可观测的活动会话或 Git 写操作时阻止启动并说明原因。该规则不是限制用户外部工具的通用文件锁。
5. 复用实时消息、审批、问询和停止能力，在任务页展示执行状态与会话入口。关闭页面后后台继续；后台进程重启后通过原生会话和持久化记录核实，无法确认时显示待核实。
6. 记录各项目起始 HEAD 和已有修改情况，复用目录改动预览。共享或已有修改目录显示累计改动，不能将全部 diff 声称为本次执行产出。
7. 展示执行摘要、验证命令及其结果、未完成项，区分 agent 声明和可核对证据。人工选择验收通过或需返工；返工可补充当前尝试或创建下一次尝试。

验收标准：

- 能配置两个使用同一 agent 的不同 bot，手动选择其中一个完成单仓库任务，并追溯实际生效配置。
- 双仓库任务可以明确选择两个目录；执行后能逐项目检查结果，记录跨仓库接口验证，缺失任一必要验证时不自动通过。
- 连续点击开始、网络重试和启动响应丢失均不会产生重复执行；结果不明时有核实入口。
- bot 占用的主目录、额外目录及父子重叠目录不会同时开始另一项受管理的写执行；不同独立目录可以并行。
- 等待审批、主动停止、执行失败与 agent 正常结束可区分，正常结束后任务仍等待人工验收。
- 刷新页面可恢复执行信息；后台重启后不会将未知执行显示为成功，也不会自动重跑。
- 调整 bot、目标、任务目录或归档任务后，历史执行快照与验收仍可查看；重新执行使用重新校验的现场。
- 新数据覆盖数据库迁移及元数据导入导出；已有任务和普通会话入口继续可用。

首个版本边界：手动创建任务、Codex bot、人工指派与验收；不依赖 issue 接入、第二种 agent 或自动调度。

## 阶段 2 从一个任务源导入 issue

解决的问题：将已经存在的需求带入任务工作现场，减少标题、说明和来源的重复录入。

实施内容：

1. 首个来源暂按 GitHub Issues 规划；如实际主要任务来自其他系统，在本阶段开始前替换选择，不同时实现多个连接器。
2. 支持粘贴 issue 链接或按需选择 issue，预览标题、说明、原始链接和源端状态；确认参与项目后，复用现有创建任务流程。
3. 保存稳定外部身份和导入快照。默认同一 issue 不重复创建任务，重复导入时打开已有任务；首版一个任务可关联多个来源引用，同一来源引用默认关联一个本地任务。
4. 通过手动刷新更新来源快照，展示与本地目标的差异，保留用户编辑。本地验收与源端关闭状态分别显示。
5. 来源不可访问时保留本地任务和已导入内容，支持重新连接；凭证使用现有环境凭证或专用安全存储，任务记录仅引用连接身份，不保存明文凭证。

验收标准：

- 从真实 issue 导入后能选择项目、准备 worktree、指派 bot、人工验收，整个流程可完成。
- 相同 issue 重复导入不重复创建任务；不同仓库或实例中的同号 issue 不混淆。
- 源端说明更新后，本地目标不会被静默覆盖；任务执行仍能追溯开始时采用的版本。
- 源端已关闭、本地未验收等差异可见，不自动关闭另一端记录。
- 认证失败、issue 无权限、网络中断不留下重复任务或半份来源关联；已有本地任务仍可工作。

本阶段不做后台全量同步、Webhook、双向状态同步或自动发布评论。

## 阶段 3 接入第二种 coding agent

解决的问题：允许任务按需要选择执行工具，验证 bot 是否能够承载不同 agent 的实际差异。

实施内容：

1. 根据真实使用选择第二种 agent。先验证其安装登录、启动、事件获取、停止及恢复方式，再确定首版能力范围。
2. 从 Codex 现有链路提取实际共用的适配接口，至少表达可用性、创建执行、状态事件、终止和结果。继续会话、审批、附件和历史读取按能力声明，不伪造统一支持。
3. 将会话引用升级为环境、agent 提供方和原生会话标识的组合，迁移已有引用、草稿、缓存、请求记录和前端控制器键；旧记录归入 Codex。
4. bot 保存具体提供方；执行记录继续使用相同任务和验收流程。切换 agent 默认新建会话，并由用户选择交接摘要。
5. 检查本机、WSL 的支持范围；不可用组合显示明确原因，不回退到另一个环境执行。支持范围与能力限制写入界面及文档。

验收标准：

- 两种 agent 都能完成阶段 1 的最小执行与人工验收流程；仅能打开外部终端、无法确认执行状态的工具不能算作完整接入。
- 相同原生会话 ID 出现在不同提供方或环境时，消息、停止操作和任务引用不串用。
- 不支持的附件、继续或审批操作在发送前有明确提示，不会发送到错误会话。
- 在运行中停止第二种 agent 后能确认已停止；连接丢失时显示待核实，不将断连当作完成。
- 旧 Codex 会话历史、关联、草稿、审批及导入导出通过迁移回归。
- 同一任务更换 bot 后保留前一次执行和验收，能够比较结果及返工原因。

## 阶段 4 验证多来源接入并提供 bot 推荐

解决的问题：任务来自多个实际系统时统一准备现场，并减少重复判断该选哪个 bot 的成本。

实施内容：

1. 当真实任务确实来自第二个系统时，复用来源身份、导入快照和刷新规则接入第二来源；没有需求时跳过连接器扩展，不影响推荐能力的验证。
2. 为 bot 增加适用项目和能力标签；结合环境可用性、目录需求及用户最近选择推荐 bot。
3. 首版使用可解释的规则推荐，展示匹配依据、限制和候选；不将 bot 自述标签当作经过验证的能力评分。
4. 记录用户接受或修改推荐的结果，复用人工验收和返工信息，为后续调度提供依据。

验收标准：

- 若交付第二来源，两来源的同号 issue、不同账号范围和重复导入均能正确区分；两者复用同一套本地任务执行与验收。
- 不可用、已停用或不支持所需环境的 bot 不会被推荐为可直接执行的候选。
- 相同输入及相同规则得到可重复的推荐，界面能解释推荐原因；用户始终可以改选。
- 没有合适 bot 或需求不明确时保持待人工选择，不强行给出答案。
- 建议连续记录至少 20 次真实选择，包含接受、改选及原因。该数量用于初步复盘，不作为推荐准确率的统计保证。

## 阶段 5 按规则自动分配和排队

解决的问题：对已形成稳定指派习惯的任务，省去重复选择，同时控制执行资源与目录竞争。

实施内容：

1. 增加显式启用的规则，例如指定项目或标签使用指定 bot。自动执行仅接收已确认项目、目标与验收条件的任务，外部 issue 导入不直接触发执行。
2. 增加队列和 bot 或环境并发额度。复用阶段 1 的启动、占用和幂等机制，调度只决定何时调用同一执行入口。
3. 保存分配来源、规则版本和命中原因；多条冲突规则进入人工处理，未命中任务保持待分配。
4. 提供暂停规则、暂停队列和取消排队。已运行任务使用现有停止操作；不能因停用规则而假装已经停止进程。
5. 只对明确尚未执行的操作进行有限重试；执行是否开始不明时核实状态，不自动创建另一次尝试。

验收标准：

- 批量提交至少 10 个模拟任务，验证并发上限、规则冲突、无匹配规则、等待目录释放和取消排队。
- 两个并发调度请求争抢同一任务或目录时，最多一个成功开始；多目录任务不会持有部分占用而无限等待。
- 队列重启、重复事件和响应丢失不造成重复派发；已运行与待核实任务不会被当作待执行任务重新启动。
- 排队期间目标、目录、bot 配置或归档状态变化时，启动前重新校验；影响执行含义的变化要求重新确认快照。
- 自动分配后仍由人工验收；任一任务可以停止自动流程并手动指定 bot。
- 建议至少完成 20 个真实任务的试用，逐项复盘错派、返工、重复启动和等待原因。出现重复启动或失去停止控制时，暂停自动派发并修复。

## 阶段 6 受限试验任务分配机器人

解决的问题：规则无法覆盖但上下文相对明确的任务，需要根据多个候选 bot 的条件做选择。

实施内容：

1. 先运行观察模式：机器人给出候选、理由或“需要补充信息”，人工继续分配；对比阶段 5 的规则结果。
2. 输入仅包含经确认的任务目标、项目、验收条件、bot 能力与可用性、历史结果摘要；模型输出限定为选择候选 bot 或拒绝分配。
3. 由确定性的调度代码重新检查候选、权限、环境、并发和目录占用；分配机器人不能自行扩权、注册 bot 或改写任务目标。
4. 仅在人工选定的项目和任务类型内开启自动试验，设置每次运行的分配数量、调用次数和可执行的任务重试次数上限；支持立即关闭和回到规则分配。
5. 复用同一执行与验收链，不在本阶段加入自动拆解任务、多 bot 互相委派、自动合并代码或发布。

验收标准及继续投入条件：

- 观察模式覆盖至少 20 次人工复核；无合适候选、信息不足和输出非法时均能保持未分配。
- 模型调用失败、超时或成本额度用尽，不改变任务已有指派，不产生新执行。
- 所有分配可追溯输入快照、候选、选择理由、人工纠正和最终验收结果。
- 自动试验可随时关闭；重复调度事件不会突破任务数、调用数或执行重试次数上限。
- 扩大试验前先约定比较口径。建议初始门槛：相近项目和任务类型各收集至少 20 次分配记录，机器人方案的人工分配耗时中位数比规则方案减少至少 20%，首次验收通过率不下降、每任务人工返工次数中位数不增加，重复派发和突破额度均为 0。这是试用决策门槛，不代表统计结论；任务构成不可比时继续观察。
- 如果大多数任务适合同一 bot，或人工分配本身耗时很少，保留默认 bot 或规则分配，暂停智能调度投入。

## 开发拆分与验证方式

预计涉及模块如下。新增模块的名称在对应阶段设计时确定，不为远期能力提前重构现有执行链。

| 阶段 | 复用或调整的位置 | 新增职责 |
| --- | --- | --- |
| 0 | `AGENTS.md`、`docs/session-architecture.md` 的现行约定 | 后续实现的状态与验收设计 |
| 1 | `internal/task`、`internal/session`、`internal/store`、`internal/model`、`frontend/workspace` 及对应 `web/features` 控制逻辑 | Bot 配置、持久化执行与验收、受管理执行的目录占用 |
| 2 | 任务创建入口、设置、数据库及元数据导入导出 | 首个来源连接、外部身份与快照、导入去重 |
| 3 | `internal/codex`、`internal/session`、`internal/workspace`、前端会话标识与缓存 | 第二 agent 适配、能力声明和提供方身份迁移 |
| 4 | Bot 配置、来源导入、任务指派入口与执行结果 | 第二来源适配、推荐理由与改选记录 |
| 5 | 阶段 1 的唯一执行入口、目录占用及数据库 | 持久队列、并发额度、规则分配与恢复 |
| 6 | 阶段 4 的推荐输入与阶段 5 的规则校验和调度 | 分配机器人观察模式、受限试验与比较记录 |

阶段 1 建议拆成四个可独立检查的小交付，顺序如下：

1. Bot 配置、执行记录结构及迁移，完成设置持久化与历史快照。
2. 任务页手动开始执行，完成上下文确认、目录占用、启动幂等与状态恢复。
3. 结果与验收，完成验证证据、返工、人工接手及目标版本处理。
4. 双仓库和重启场景验收，补齐导入导出及旧流程兼容。

阶段 2 和 3 各自通过后再合并验证“外部 issue → 多项目任务 → 选择不同 agent 的 bot → 查看改动 → 人工验收”。一个阶段不通过，不用新增连接器或调度能力掩盖问题。

各实现阶段复用现有检查：前端类型检查与构建、聊天与工作台回归、Go 测试与 vet、相关包 race 检查，以及独立任务流程 smoke。具体命令以 `.github/workflows/checks.yml` 为准；涉及桌面宿主、环境传输或打包时再运行相应平台验收。

新增自动化检查优先覆盖会导致错误执行或丢失数据的场景：重复启动、目录交叉占用、环境串用、停止失效、重启核实、迁移及来源去重。使用临时数据目录、临时 Git 仓库和确定性假 agent；真实 agent 与真实 issue 的验收由显式选定的样例执行，记录结果，不消耗日常项目作为自动测试现场。

每个里程碑保留一份简短验收记录，包括样例、通过与失败项、遗留问题和下一阶段进入条件。本次计划整理没有执行产品测试，也不将已有能力描述视为本轮重新验收通过。

## 评价指标和暂缓范围

从阶段 1 开始记录人工准备时间、执行耗时、需要人工介入的次数、首次验收结果和返工原因；阶段 4 增加推荐接受或改选记录，阶段 5 增加队列等待、错派和重复执行记录。agent 未提供可靠费用时标记未知，不估造成本数据。初期用执行记录和简单汇总复盘，不新增独立分析平台。

任务数、执行次数和 bot 数量分别统计；首次验收通过以任务首次提交验收的结果计，返工后成功不能覆盖首次失败。中止、需求变化和环境故障单独标注，避免错误归因于 bot 能力。

近期暂缓团队协作与组织权限、机器人市场、常驻机器人社交账号、通用 DAG 工作流、自动任务拆分与多 agent 辩论、全量双向 issue 同步、跨环境单次执行，以及无人验收的自动合并和发布。出现具体需求时，再按“是否改善任务组织跨项目开发、能否复用现有能力”重新评估。

下一步优先实施阶段 0 的执行约定和阶段 1 的四个小交付。阶段 1 独立构成可日常使用的版本，后续来源和 agent 扩展均建立在这条闭环之上。
